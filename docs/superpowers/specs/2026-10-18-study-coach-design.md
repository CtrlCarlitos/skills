# `study-coach`: design

## Intent and why

The user's kids (El Salvador, grades ~3rd-5th, ages 8-10) sometimes struggle with school subjects -- Spanish grammar specifically called out as unusually hard for this age -- and the user wants a way to (a) know, concretely, where a kid actually stands against what their grade is supposed to know, and (b) build real material (video, flashcards, exam) to close specific gaps, grounded in what the school actually teaches rather than a generic AI answer.

Two real moments drive this, both described directly by the user:

1. **The panic gap.** The user's kid can discuss a subject fluently one-on-one, then freezes and underperforms on the actual exam. The user's own words: "I'm trying to build confidence in the subject, and specially in the child." This is a distinct problem from "doesn't know the material" -- it's exam-format unfamiliarity and performance pressure, and the design has to treat it as its own thing, not something a generic "make it fun" gamification layer happens to fix.
2. **Nobody likes to study.** Separately from confidence, review itself is boring, and that's worth addressing with its own mechanic (points/streaks/game layer on flashcards and practice), not conflated with the confidence-building layer above.

A third, equally real driver: sometimes the user's own kid asks a question the user can't answer, or isn't sure how to answer the way the school actually teaches it. The user wants an AI answer that's cross-checked against the actual curriculum, not just confidently generated -- because a technically-correct answer using the wrong term, or a method the teacher hasn't introduced yet, actively confuses a kid this age rather than helping.

**Why a new skill, not an extension of the existing `teach` skill** (the user's own comparison point, confirmed by direct inspection of `teach`'s `SKILL.md` before this design was written): `teach` is built for one curious adult, self-directed, over a long-running single-topic workspace, producing HTML lesson pages with lightweight in-lesson quizzes -- no video, no audio, no flashcards, no gamification, no exam generation, no curriculum/ministry-standard alignment, nothing kid-specific. `study-coach` is a different shape of problem: a parent generates a full multi-artifact bundle *for* a child who never operates the tool directly, grounded against an external, country-specific curriculum standard, with a confidence-building design goal `teach` has no equivalent of. Forcing this into `teach` would mean bending it past recognition or bolting on a parallel mode sharing almost nothing. `study-coach` does reuse `teach`'s core philosophy where it actually applies: **ground in cited, high-trust sources, never recite parametric/memorized knowledge as if it were verified** -- see "Grounding strategy" below.

**Validation plan, stated directly by the user, shapes scope:** this is being built to test on the user's own kids first. If it works, a multi-family/teacher platform (possibly a mobile app) is the next idea -- explicitly **not** part of this project. Every design choice below should make sense for "one family, validating an idea," not "day-one infrastructure for a product."

## Goals

- A parent can generate a full learning bundle for one topic within one subject: a short narrated video, flashcards, and an exam, for a specific kid, grounded against the best available authoritative source for that topic.
- A parent can generate a smaller, narrower artifact (not necessarily the full bundle) in response to a kid's specific stuck question, same grounding discipline, smaller scope.
- After an exam, the parent gets a report that identifies *which specific competencies/topics* the kid has and hasn't got down -- not a bare score.
- The confidence-building design goal is real and separate from the fun/engagement design goal: low-stakes practice that mimics the real exam's format and shows visible progress, distinct from a points/streaks layer on flashcards and review.
- Works for any topic, not just official school subjects -- a school subject grounds against the curriculum; a non-curricular topic (e.g. "how to start a YouTube channel") grounds against the best current real sources on that topic instead. Same pipeline either way.
- Delivery language is a parameter independent of the language the parent writes the request in (write in English, get a Spanish bundle, for this family's actual case).
- Everything the kid touches is pre-generated and self-contained before they see it -- a video file, flashcard pages, an exam page that grades itself. The kid never operates Claude Code, a CLI, or any back-and-forth chat themselves.
- One `study-coach/` home workspace per family, not one folder per session (contrast with `teach`), with subjects/topics organized underneath it and a single navigable `index.html` front door showing a running, longitudinal view of how each subject/topic is tracking across exams over time.

## Non-goals (for this project)

- No mobile app, no multi-family or teacher-facing platform, no account system, no server/backend of any kind. This is local files a parent generates and a kid opens in a browser/video player, full stop, for this iteration.
- No support for countries/curricula other than El Salvador's MINEDUCYT for this build. The design should not accidentally make a different country harder to add later, but no second country's content ships now.
- No paid TTS/cloud voice service integration for this phase -- local only (see Constraints). Swapping in a paid "best available" service is explicitly deferred to a later, separate decision if/when this moves past validation.
- No attempt to algorithmically detect or adapt to a kid's emotional state in real time (e.g. during the exam) -- "confidence building" here means pre-exam practice design and post-exam reporting, not live biometric/behavioral adaptation.
- No general-purpose spaced-repetition scheduling engine (e.g. a full SM-2/Anki-style algorithm) unless a simpler "track what they keep missing, resurface it more" mechanic turns out to be insufficient in practice -- start simple, this is explicitly left open to the builder to size correctly rather than over-build.

## Anti-goals

Would count as a failure even if it technically ran:

- A kid encountering a term or method in the generated material that contradicts what their teacher actually uses, because nothing was actually grounded against a real source -- this is the single most important thing to get right, called out by the user twice independently (once about cross-checking ad-hoc answers, once about Santillana/MINEDUCYT alignment).
- A report to the parent that's just a score with no indication of *what* to work on -- the user was explicit that the whole point is knowing where more learning is needed, not a pass/fail number.
- A video, flashcard set, or exam so long or joyless that it recreates the exact boredom problem it's meant to solve.
- Treating "gamification" as a single generic feature bolted on at the end, collapsing the two distinct jobs (confidence-building low-stakes practice vs. engagement/fun) the user was specific about keeping separate.

## Constraints

- **TTS: local only, for this phase.** Confirmed via direct research before this doc was written: Ollama itself does not do text-to-speech (it's text-generation only) -- the user's mention of it was shorthand for "something local and free," not a literal requirement. The actual local engine: **Kokoro** (Apache-2.0 license, confirmed Spanish support, ~82M params, CPU-friendly, realistic to run in Docker). TTS engines, including Kokoro, do not reliably emit word-level timing on their own -- the standard, more-accurate-than-blind-transcription pattern is to generate audio first, then run a **forced-alignment** pass against the already-known script text. **WhisperX** is the recommended alignment tool over `whisper-timestamped`, specifically to avoid the latter's GPL v3 `dtw-python` dependency -- a real licensing constraint for anything in this repo, which the builder should confirm against this repo's own license before finalizing. WhisperX has a known weakness aligning digits/symbols, so numbers in any script should be normalized to words before alignment (e.g. "3" -> "tres").
- **Curriculum source coverage is uneven, confirmed live, not assumed.** El Salvador's MINEDUCYT (mined.gob.sv) publishes real, directly-linkable PDFs, but coverage for the 3rd-5th grade range is inconsistent: Matemática has actual textbooks for 2nd-3rd grade; Lenguaje y Literatura has official guides for 2nd, 7th, and 8th grade, but **not currently for 3rd-5th** -- the family's own target range. No formal "Programa de estudio" (competency-level syllabus, not just a textbook) was found for this range in either subject. The user's Santillana textbook (the one the school requires) could not be verified online at all -- no table of contents, no confirmed MINEDUCYT-alignment claim. This means the grounding strategy cannot assume MINEDUCYT alone is sufficient for every subject/grade combination that will come up.
- **Remotion has no existing TTS-alignment integration pattern** that research turned up -- converting the alignment tool's word timestamps into Remotion's frame-based timing is net-new integration work, not a known off-the-shelf path.
- No TTS engine's actual Spanish *voice quality* (as opposed to just "supports Spanish") has been independently verified for this use case -- only vendor/model-card self-reports exist. Worth a real listening check early in implementation, before building the full pipeline around a choice that turns out to sound robotic to an 8-year-old.

## Decided (the parts of the how already settled in this conversation)

- **Name:** `study-coach`.
- **Two entry points, one engine:**
  1. *Full bundle* (parent-initiated): subject + topic in -> video + flashcards + exam + (after the kid takes the exam) a topic-tagged gap report.
  2. *Quick answer* (parent-initiated on the kid's behalf, narrower): one stuck question in -> a smaller artifact (short explanation, maybe a few flashcards) -- not necessarily a full video+exam bundle. Same grounding discipline as the full bundle, smaller scope.
  Both entry points are invoked by the parent; the kid is never the one operating Claude Code or any CLI.
- **Grounding strategy, dual-mode by topic type:** a school-curriculum topic grounds against MINEDUCYT where it exists for that grade/subject, falls back to the family's own Santillana book (parent-supplied photos/scans) where MINEDUCYT's coverage has gaps (confirmed real for Lenguaje, grades 3-5), and states explicitly in the generated material which source backed which part -- never silently blending an ungrounded claim in. A non-curricular topic (YouTube channel, programming, anything outside the school's subjects) grounds against the best current real sources on that specific topic instead -- same "cite it, don't just recite it" discipline `teach` already uses, applied to a different kind of source.
- **Video:** short, modular segments (2-4 minutes each, chunked by sub-topic) rather than one long fixed-length video -- easier to re-watch just the part that didn't land, avoids a single video having to be perfect start to finish. A character appears at the start and end of a segment and occasionally mid-segment to check in -- not a constant on-screen presence. Built with Remotion; narration audio from Kokoro, word-level timing from WhisperX, used to drive caption/visual timing in the Remotion composition.
- **Flashcards:** digital-first -- an on-screen deck, tap/click to reveal the answer, tracks which ones the kid keeps getting wrong so those resurface more. A printable export is a secondary, optional output for families with a printer (confirmed the user has one; also confirmed not every family will), not a requirement every deck must satisfy equally well.
- **Exam format:** not grounded against a real past exam sample -- the parent doesn't have one to hand, so the exam uses a varied, builder-designed mix of common question types: multiple choice, single-select (radio), fill-in-the-blank, and open/free response, plus true/false and matching as reasonable additions. Every question is tagged to the specific competency/topic it tests regardless of type, so results aggregate into a per-topic breakdown -- the thing the user asked for by name -- not a single score.
- **Exam grading, split by question type:** multiple choice, single-select, true/false, matching, and fill-in-the-blank (exact or close-match text) all grade themselves client-side in the self-contained HTML, since the correct answer is already known at generation time. Open/free-response questions cannot self-grade that way -- there's no backend to evaluate free text against. These get folded into the same already-settled "parent brings results back to the next `study-coach` invocation" flow used for persistence in general: the kid's written answer is captured in the results export, and grading/topic-tagging for just the open-response items happens when the parent next invokes the skill, not instantly on the page.
- **Parent report:** built from the exam's topic-tagged results; shows what's solid and what needs more work, and (per the home-workspace decision below) persists so the `index.html` dashboard can show a trend across topics and over time, not just the latest exam in isolation.
- **Confidence-building layer (distinct mechanic #1):** low-stakes practice that mimics the real exam's actual format and question style, so the exam format itself is familiar before it counts, plus a visible "how much of this you already know" progress indicator -- built to directly counter the panic-despite-fluency pattern the user described, not generic reassurance copy.
- **Engagement layer (distinct mechanic #2):** points/streaks/a lightweight game layer specifically on the flashcard/review experience, to counter plain boredom -- kept conceptually and (likely) technically separate from the confidence layer above, since they solve different problems and the user was explicit they shouldn't be collapsed into one generic "gamification" feature.
- **Language:** the language the parent writes the request in and the delivery language of the generated material (video narration, flashcards, exam -- everything kid-facing) are independent parameters. Defaults to Spanish for this family's actual use, but the parameter itself is general, not hardcoded to Spanish.
- **Workspace layout:** one `study-coach/` home per family (not one folder per session, unlike `teach`), subjects/topics organized underneath it, shared assets (character art, CSS, the quiz/exam-widget JS, voice samples) reused across all lessons rather than duplicated per topic -- same reuse-by-default convention `teach` already uses for its own shared assets. A single `index.html` is the navigation front door: browse to any subject/topic's material, and see the longitudinal per-topic dashboard described above.
- **Workspace location, confirmed with the user:** `CtrlCarlitos/skills` is a public GitHub repo. The *skill itself* (the code that builds bundles) ships in this repo like every other skill here; the *family's actual `study-coach/` workspace* -- real kids' names, grades, exam history, and any Santillana page photos -- lives entirely outside this repo, in a private local folder, never committed or pushed. The skill must be built so pointing it at an out-of-repo workspace path is the normal case, not a special mode.
- **Scope of subjects:** not limited to a fixed list -- any topic can go through the same pipeline, curricular or not, per the dual-mode grounding strategy above.
- **State persistence, despite "no backend" (my call, flagged by the builder check as load-bearing and otherwise unaddressed):** a static exam/flashcard page cannot silently write back to the workspace or update a sibling `index.html` on its own. The exam ends by producing a results export (a downloadable file); the parent brings that back into their next `study-coach` invocation, and that's the point at which the persisted report and the `index.html` dashboard actually update. This keeps the "no backend" constraint intact (nothing runs or listens continuously) at the cost of one manual parent step between "kid finishes the exam" and "dashboard reflects it" -- a reasonable tradeoff for a single-family validation build, revisit if it proves annoying in practice.
- **Multi-child (my call):** the workspace is explicitly multi-child-aware. Each kid gets their own partition under the family's `study-coach/` home (own subject/topic progress, own exam history, own dashboard view) -- not a shared pool that would conflate one kid's results with another's. The exact directory naming is still the builder's to decide (per "What's left to the builder" below), but *that* there is a per-child axis is settled, not incidental.
- **Santillana ingestion (my call):** ad hoc and just-in-time, not a one-time bulk-scan step -- the parent supplies a photo of the relevant page(s) only when a specific topic actually needs it (MINEDUCYT's gap, confirmed real for Lenguaje grades 3-5). Whatever gets supplied is kept and reused if the same page is relevant again later, so a source library accumulates naturally over time rather than requiring the parent to scan an entire textbook upfront on the chance some of it might be needed eventually.

## What's left to the builder

- The exact `study-coach/` directory structure under the home workspace (subjects/topics/quick-questions/assets layout) -- the plan should propose one, informed by `teach`'s own existing conventions where they transfer.
- The exact shape of the topic-tagging taxonomy for exam questions (how fine-grained a "competency" is, how it's recorded, how the report renders it) -- informed by whatever structure actually exists in MINEDUCYT's published materials once a specific subject/topic is implemented, since the available detail varies by subject (confirmed: Matemática has more formal structure available than Lenguaje for this grade range).
- Concrete game mechanics for the engagement layer (point values, streak rules, what a "level" is, if anything) -- the user described the *purpose* clearly (kill boredom, keep it separate from confidence-building) but not specific mechanics; reasonable for the builder to propose and size small for a first version.
- The specific low-stakes-practice format for the confidence-building layer (e.g., an untimed mock exam using the same question bank/format as the real one, taken as many times as wanted before the real one) -- the user named the goal, not the mechanic.
- Visual/character design -- a consistent, reusable character asset the Remotion compositions can pull in, appropriate for an 8-10 year old audience.
- The real listening-quality check on Kokoro's Spanish voice output before committing the full pipeline to it, per the Constraints section -- if it sounds poor, the fallback local option (XTTS-v2, confirmed Spanish-capable but GPU-dependent) should be evaluated instead, and that tradeoff (quality vs. local hardware requirement) brought back for a decision rather than silently substituted.
- Converting WhisperX's word-timestamp output into Remotion's frame-based timing model -- confirmed no existing integration pattern for this; real implementation work, not configuration.
- Whether the "quick answer" entry point produces a full mini-bundle (short video too) or text/flashcards only -- the user said it's "most likely... smaller" but didn't fully specify; reasonable for the builder to propose a default (e.g., start text+flashcards only, add a short video only if the question clearly needs visual explanation) and state it as a judgment call.
