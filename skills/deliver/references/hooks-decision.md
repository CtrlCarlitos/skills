# Git hooks: evaluated, not adopted by default

Per the issue: compare a plain verification command, native Git hooks, and the `pre-commit` framework, and choose the smallest justified solution after checking what the repository actually has -- not a default choice made in advance.

## What this repository actually has

Checked at implementation time: no `.git/hooks/*` beyond Git's own samples, no `.pre-commit-config.yaml`, no `pre-commit` listed in any `requirements.txt`. The baseline is **no hooks, no hook framework**.

## Decision

**Default: no hooks.** The smallest justified solution for a repo with zero existing hook infrastructure is not to introduce one -- `deliver`'s pre-push gate (Section 6 of the issue; `scripts/validation_contract.py`) already enforces the same local-validation contract a `pre-push` hook would, as an explicit step the skill itself runs before pushing. Adding a hook on top would duplicate that enforcement without adding a new guarantee, since `deliver` is already the thing invoking the check -- a hook only matters as a backstop against *forgetting* to invoke it, and `deliver`'s whole purpose is to not forget.

**Not the `pre-commit` framework.** It's a new dependency and a new config file for a repository that has never used it, to do something a same-language script (`validation_contract.py`, already Python, already in this repo) does directly. Per the issue's own framing, don't require a new task-runner framework when existing tooling covers it.

**Native Git hooks: now built, as an available, opt-in extension -- not the default.** Per #23, `scripts/hook_runner.py` is a non-interactive CLI over the exact same `parse_ci_steps`/`build_local_validation_contract`/`run_contract` functions Section 6 calls inline (now also filtering to only the jobs whose `runs-on` matches the current OS, so a hook on one platform never blocks a commit over a job pinned to a different one), and `scripts/install_hooks.py` installs/removes a `pre-commit` + `pre-push` pair that calls it. Worktree-compatible: the repo root is resolved inside the hook script itself, at commit time (`git rev-parse --show-toplevel`), never baked in at install time -- baking it in would validate the wrong tree the moment the hooks directory (shared across all of a repo's worktrees) is reached from a worktree other than the one `install` was run from. Never overwrites an unrelated existing hook (every hook this tool writes carries its own marker comment on the line right after the shebang; install refuses if a non-marker file, or a symlink, is already there). Never touches `git config`, and refuses by default to install into a hooks directory shared across every repo on the machine (see the hazard note below) -- `SharedHooksDirError`, with an explicit opt-out.

The hook script itself is a single POSIX-shell file (`#!/bin/sh`), which Git for Windows already executes through its own bundled shell via the shebang, the same mechanism as Linux/macOS -- no separate PowerShell variant needed *in principle*. **Not yet confirmed on real Windows CI for this specific feature** -- the unit test suite runs on `windows-latest` as part of this repo's existing CI matrix, but no PR for this work had actually been run through it as of this note; treat "works on Windows" as expected-by-design, not independently verified, until a real CI run for this branch is observed green there.

A real hazard surfaced while building this, worth recording in full because it's not just a testing lesson -- it's a real design requirement: on a machine where `core.hooksPath` is configured globally (not uncommon -- this is how some security/guardrail tooling installs its own hooks across every repo on a machine), `git rev-parse --git-path hooks` resolves to that *same shared, global* directory for every repository, including a disposable throwaway test fixture. A test that exercised this resolution during a file-write, rather than against an isolated fake, overwrote a real, pre-existing file outside any test's control, with no way to recover its prior contents. Filed as `CtrlCarlitos/agent-guardrails#542` (should an agent's writes to that location be protected) and `CtrlCarlitos/dotfiles#425` (should it be dotfiles-managed, so a recoverable copy exists).

Two separate fixes came out of this, not one: (1) the test suite now injects a fake path resolution in every test that writes a hook file, and isolates the one test that does run real git commands (`GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM`) -- that's the testing fix. (2) `install()` itself now refuses, by default, to write into a hooks directory that isn't this specific repo's own local one (`SharedHooksDirError`) -- that's the actual product fix, because the hazard isn't only a test-isolation problem: a real end user on a machine with a global `core.hooksPath` would hit the exact same thing. Installing a repo-specific validation hook into a directory shared by every repo on that machine would silently turn one repo's CI contract into a commit gate for every other repo sharing it -- a global behavior change the issue's own "no silent global git config changes" requirement is clearly trying to rule out, even though no `git config` write is involved.

## What `deliver` does instead

`deliver`'s own pre-push step *is* the enforcement point: Section 6 of `SKILL.md` says to build and run the contract before every CI-triggering push, required-push-blocking on a required failure. This happens inside the skill's own flow, not via an external hook Git invokes automatically -- which also means it works identically whether or not the human running `deliver` ever sets up a hook, and whether their host supports Git hooks at all.
