# Containers, `act` rehearsal, and OS/desktop profiles: research summary

Per the issue's own framing (sections 7-8): these are "optional," "research, not a core dependency," and must "not delay the core skill." The `act`/container section below is now confirmed live (CtrlCarlitos/skills#23); OS/desktop profiles remain research-only, no provisioning, per the issue's own explicit budget/lifecycle-approval gate.

## Containers / Docker / devcontainer-aware validation

Most work in this repository runs natively (plain `python3 -m unittest`, `bash scripts/sync-vendor.sh`) -- there is no existing Docker/Compose/devcontainer profile to integrate with yet. Building one speculatively, before any task in this repo actually needs it, would be exactly the "turn this into a container provisioning platform" the issue warns against.

**Decision for v1:** `deliver`'s local-validation contract (`scripts/validation_contract.py`) runs natively. If a future task genuinely needs a container-backed profile (reproducible image/tool versions, isolated test services), that's real, scoped work for #23 -- done against an actual need, with the image/architecture, task-source mounting strategy, and safe-permissions requirements the issue lists, not provisioned in the abstract here.

## `act` rehearsal -- confirmed live

[`act`](https://nektosact.com/) runs GitHub Actions workflows locally via Docker. Both `act` (0.2.89) and a running Docker daemon are actually installed in this project's working environment, so this was driven live against this repo's own real `ci.yml` rather than reasoned about in the abstract.

- `act --list` correctly sees all three real jobs (`vendor-check` on `ubuntu-latest`, `skill-creator-tests-windows` on `windows-latest`, `skill-creator-tests-macos` on `macos-latest`), confirming the earlier point below: **only the `ubuntu-latest` job is actually container-rehearsable** -- `act` cannot virtualize Windows/macOS in Docker; it would need `-self-hosted` runner mapping to an already-available matching host for those two, which removes container isolation entirely and proves much less than a green run looks like it proves.
- Running `act -j vendor-check` against the real workflow surfaced a concrete, reproducible divergence: the job's `pip install -r skills/skill-creator/requirements.txt` step, which has passed on every real `vendor-check` GitHub Actions run throughout this project's history, **fails under `act`'s recommended "medium" runner image** (`catthehacker/ubuntu:act-latest`) with `error: externally-managed-environment` (PEP 668) -- that image's Python enforces a restriction GitHub's actual hosted `ubuntu-latest` runner does not. `act`'s own "Large" image is documented as "snapshots of GitHub Hosted Runners" and would plausibly not have this restriction, but at ~17GB download / ~75GB storage, pulling it to confirm was disproportionate to this research task and wasn't done.
- This is exactly the kind of runner-image divergence the issue asked this evaluation to watch for, now with a first-hand, reproduced example rather than a general caveat: **a green `act` rehearsal is not proof CI will pass, and a red one is not proof it will fail** -- it can diverge from GitHub's actual hosted image in either direction.

**Decision, confirmed:** not adopted as a default step. `deliver`'s local-validation contract already runs the exact commands CI runs, natively, on the actual machine running the task -- a stronger and simpler signal than rehearsing the GitHub Actions YAML through a second tool whose own default image just demonstrably diverges from GitHub's real one on this very repo. `act` remains a reasonable *manual, occasional* tool for a human investigating action-specific behavior `validation_contract.py` can't reach (an actual `uses:` step's behavior, not just the `run:` steps) -- not something `deliver` invokes itself.

## OS/desktop profiles -- research refreshed, still no provisioning

This repository's own CI already runs on `ubuntu-latest`, `windows-latest`, and `macos-latest` (confirmed: `.github/workflows/ci.yml`) -- real coverage of all three OS families already exists at the hosted-CI level. What's genuinely missing, and genuinely optional per the issue, is desktop/GUI/interactive coverage beyond what a hosted CI runner provides (login sessions, reboot behavior, real desktop environments) -- not relevant to anything this repository's skills currently need, since none of them do GUI automation or OS-level installation testing the way dotfiles-style bootstrap work does.

**No provisioning was done; nothing below was signed up for, started, or billed.** The issue's own requirement is explicit: "No paid provisioning without separate budget/lifecycle approval," and none has been sought. What follows is a refresh of the leads against current public information (checked 2026-10-18), against the issue's own comparison criteria -- so whoever eventually picks this up has current numbers, not the original leads carried forward unchecked.

**What changed since the leads were first gathered:** AWS EC2 Mac's 24-hour *host* minimum (not per-instance) and its "billed even while stopped, until the host is released" behavior are now confirmed directly from AWS's own FAQ and a real support thread, not assumed. MacStadium Orka's pricing is confirmed node-based with no public on-demand rate (sales-quote only) rather than a number that can be compared directly. **Fly.io Sprites' fit for this issue is now in real doubt** -- current public material describes it as a Linux sandbox/coding-agent product with no mention of macOS or Windows support at all; the original lead's premise (useful for OS/desktop *profiles*, plural, implying non-Linux) isn't substantiated and needs direct verification with Fly.io, not continued assumption, before anyone treats it as a real option for this issue's macOS/Windows use case.

**Decision, unchanged:** no provisioning, no provider selection. The refreshed comparison above replaces the original leads for whoever picks this up next; the open budget/lifecycle-approval gate the issue itself requires is still open.
