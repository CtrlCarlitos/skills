name: update-docs
description: Audit a repo's documentation against its code, report what's missing/incorrect/stale with the file, line, and evidence that proves it, and -- only when asked -- fix the findings picked or write a new page for a gap. Use this whenever the user asks to check docs against code, audit documentation, find stale docs, or update/write documentation for a change -- never as an automatic follow-up to other work.
---

Keep a repo's documentation true to its code. Audit first, always read-only by default; edit or generate only when explicitly asked, and only with the smallest change that makes the doc true. The companion to `release-notes` (#2) -- that skill's "Docs to check" list is one input here, not the only one.

## Modes

### 1. Audit (default, read-only)

```bash
python3 -m scripts.gather <repo-root> [--scope diff|range|repo] [--base <tag-or-commit>] [--head <commit>] [--type <type-name>]
```

Run from this skill's directory (`skills/update-docs/`). Prints JSON: the repo-type guide, which docs are in scope, the full set of tracked docs (for searching stale references outside the diff -- see Rule 2 below), which in-scope docs are machine-generated, and the three optional checkers' results. This step is purely mechanical and writes nothing.

`--scope diff` (the default) means uncommitted changes against `HEAD`. `--scope range` resolves `--base`..`--head` (use this for "audit the docs for this range/PR"). `--scope repo` audits everything -- only run this when asked for a whole-repo audit.

For each doc in scope, find every claim about the code and check it against the code itself:

- **Code is the source of truth (Rule 1).** Every finding cites what proves it wrong or missing: a file and line, a command's `--help` output, or a test. A finding with no evidence doesn't get reported.
- **Scope to the change (Rule 2).** `docs_in_scope` is what the diff/range touched directly. But also search `all_doc_files` for the old name/term of anything renamed or removed in the diff -- a doc elsewhere that still mentions it is in scope too, even though it wasn't itself changed.
- **Read the repo-type guide** (`repo_type.guide` in the JSON) for what counts as the public surface to document, what's generated and by which command, and "don't document" markers specific to this ecosystem.
- **Check `generated_docs`** before treating any finding in one of those files as fixable by hand -- Rule 4 below.
- **Sort findings into missing, incorrect, or stale** -- missing (no doc exists for a public thing), incorrect (a doc makes a claim the code contradicts right now), stale (a doc was true once but the code moved on, e.g. an old flag name, a planned feature that shipped differently or not at all).

Report the three optional checks' results (`checks.markdownlint`, `checks.lychee`, `checks.vale` in the JSON) verbatim -- each has `ran`/`passed`, and `ran: false` means the tool wasn't available, which is normal, not a failure to report as such. Confirmed live against a real repo's docs: a lychee "broken" result can be a 403 from a site blocking automated requests (npmjs.com does this), not an actually dead link -- spot-check a `broken` entry before reporting it as such if the status looks like bot-blocking rather than a real 404/DNS failure.

Then report, per Rule 9: the findings (missing/incorrect/stale, each with its evidence), the findings left alone and why (e.g. "the ADR at docs/adr/0003 is accepted, not touched"), and the docs checked that had nothing wrong.

### 2. Update (on request)

Fix only the findings the user picks. For each:

- **Minimal edit (Rule 3).** Keep the existing wording, structure, and any uncommitted edits already in the file. Remove text that misleads rather than bolting a warning next to it. After a rename, search `all_doc_files` for the old term and fix every occurrence, not just the one originally flagged.
- **Generated docs go through their generator (Rule 4).** If `generated_docs` (or the repo-type guide) says a doc is generated, change the source it's generated from and regenerate -- never hand-edit the generated output. If you can't run the generator, say so and stop; don't approximate its output by hand. The flag can mean the *whole* file or just a marked section within it (confirmed live: a real repo's doc had a `<!-- ...-begin (generated by ... - do not edit by hand) -->` / `-end` pair around one table, with ordinary hand-written prose around it) -- check for begin/end markers before assuming the entire file is off-limits.
- **Setup first (Rule 5).** When several findings compete for attention, fix install/quickstart/config docs before reference pages.
- **Hands off other records (Rule 6).** Never edit `CHANGELOG.md` (that's `release-notes`'s job), an accepted ADR, or a version number. Never auto-edit a diagram (Mermaid, ASCII) -- flag it as a finding instead and let a person redraw it.
- **No future fiction (Rule 7).** Document what the code does now. If a doc describes a planned feature that doesn't exist yet, that's a finding (remove or correct it), not something to leave "for later."
- **Re-run the checks** (`scripts/markdownlint_check.py`, `scripts/linkcheck.py`, `scripts/prose_check.py`, or re-run `gather.py`) after editing, and report before/after.

### 3. Generate (on request)

Write a new page for a confirmed gap.

- **Classify the page first.** Use `references/diataxis.md`'s concrete signs (not just the name) to decide tutorial, how-to, reference, or explanation, and place it where the repo's existing structure (or the repo-type guide) says that kind of page lives.
- **Still cite evidence (Rule 1).** A new page describes real, current behavior -- back every claim in it the same way an audit finding would be backed.
- **Reader test.** For a new or substantially rewritten page, spawn a subagent with no context on this conversation or the code -- only the page's own text -- and have it answer 5 to 10 questions a real reader would likely have after reading it (e.g. "how do I undo this?", "what happens if X is missing?", "what does this cost?"). Report which questions it couldn't answer from the page alone; those are the gaps to close before presenting the page as done. A subagent that can answer everything confidently from a thin page is not a passing result -- check whether it's actually finding the answer in the text or guessing.
- **Lint and link-check the new page** the same way Update mode does.

## Optional checks

Each tool is used if installed, otherwise the check is reported as skipped -- never a hard dependency:

- `scripts/markdownlint_check.py` wraps `markdownlint-cli2` (installed binary, falling back to `npx markdownlint-cli2` if only Node is present). No config is passed by default, so its own auto-discovery finds the *repo's own* config (Rule 8) -- this skill ships none of its own, unlike `release-notes`, since there's no house format to enforce on someone else's repo.
- `scripts/linkcheck.py` wraps `lychee`. Same auto-discovery approach (no config passed unless the repo has its own `lychee.toml`, which lychee finds on its own via `cwd`).
- `scripts/prose_check.py` wraps `vale`. Unlike the other two, vale can't run meaningfully with no config at all -- it errors. The repo's own `.vale.ini` wins if present; otherwise this skill's built-in config (`references/vale/.vale.ini`, declaring the Google developer documentation style) is copied into a cache dir and synced with `vale sync` on first use (confirmed live: this works over the network, no vendored style files shipped). If the sync fails (no network) and the repo has no config of its own, prose-checking is skipped, same as any other unavailable optional tool.

## Repo types

Same mechanism as `release-notes`, and the same built-in types: generic, odoo, phoenix, go, flutter, course, docs -- in `references/`. Lookup order (first match wins): the repo's own `.update-docs/type.md`, then `~/.config/update-docs/types/<name>.md`, then built in. `references/writing-a-type.md` explains the required sections and how to write your own.

## What this skill does not do

- Never runs on its own after other work -- only when explicitly asked.
- Never writes or edits anything in Audit mode; Audit is always read-only.
- Never touches `CHANGELOG.md`, an accepted ADR, or a version number (Rule 6) -- those are either `release-notes`'s territory or out of scope entirely.
- Never auto-edits a diagram -- flags it for a person instead.
- Never documents a planned-but-unshipped feature as current behavior.
- Does not host a docs site, choose a site generator, handle translation, or write marketing copy.
