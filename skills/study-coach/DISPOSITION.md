# `study-coach`: audit and scope decisions

For the user's own kids (El Salvador, grades ~3rd-5th). This covers all three plans of the spec's "study-coach v1" (+1 video plan, deferred to its own later issue). Full design: `docs/superpowers/specs/2026-10-18-study-coach-design.md`.

## Audit summary

Why a new skill, not an extension of the existing `teach` skill (`~/.claude/skills/teach/`, read directly before this design was written): `teach` is built for one curious adult, self-directed, over a long-running single-topic workspace, producing HTML lesson pages with lightweight in-lesson quizzes -- no video, no audio, no flashcards, no gamification, no exam generation, no curriculum/ministry-standard alignment, nothing kid-specific. `study-coach` is a different shape of problem: a parent generates a full multi-artifact bundle *for* a child who never operates the tool directly, grounded against an external, country-specific curriculum standard, with a confidence-building design goal `teach` has no equivalent of. `study-coach` does reuse `teach`'s core philosophy where it actually applies -- ground in cited, high-trust sources, never recite parametric/memorized knowledge as if it were verified -- see the Grounding strategy below.

## Scope decisions (confirmed with the user before implementation)

Recorded verbatim from the design doc's "Decided" section, settled before this plan was written:

1. **Two entry points, one engine, implemented in Plan 3 (documented as SKILL.md recipes, not pre-built Python, since content generation is inherently the invoking session's job):** *full bundle* (subject + topic in -> flashcards + exam + post-exam gap report; video remains deferred) and *quick answer* (one stuck question in -> flashcards only by default). Both parent-initiated; the kid never operates Claude Code or any CLI.
2. **Dual grounding strategy, implemented in this plan:** a curricular topic grounds against MINEDUCYT where it has real coverage for that grade/subject, falls back to the family's own Santillana photos where MINEDUCYT's coverage has gaps (confirmed real for Lenguaje grades 3-5), and states explicitly which source backed which part -- never silently blending an ungrounded claim in. A non-curricular topic grounds against general sources instead, same "cite it, don't just recite it" discipline.
3. **Multi-child-aware workspace, implemented in this plan:** each kid gets their own partition under the family's home workspace -- not a shared pool that would conflate one kid's results with another's.
4. **Workspace lives outside this repo by default, implemented in this plan:** `CtrlCarlitos/skills` is a public GitHub repo (confirmed via `gh repo view`); the family's real data (kids' names, grades, exam history, Santillana photos) must never live inside it. Every function in this plan takes an explicit `workspace: Path` argument -- nothing hardcodes or assumes a path inside `skills/study-coach/`.
5. **Santillana ingestion is ad hoc and accumulating, implemented in this plan:** the parent supplies a photo only when a specific topic actually needs it, not a one-time bulk scan. A second photo for the same subject/topic adds to the cache, never overwrites the first.
6. **Exam question types and grading split, implemented in Plan 2:** multiple choice, single-select, fill-in-the-blank, true/false, and matching all self-grade client-side in static HTML; open/free response cannot self-grade without a backend, so it's folded into the already-settled "parent brings results back to the next invocation" flow used for persistence in general.
7. **State persistence despite "no backend", implemented in Plan 2:** the exam page produces a downloadable results export; the parent brings that back into the next invocation, which is where the persisted report and dashboard actually update. Nothing runs or listens continuously.
8. **Flashcards are digital-first, implemented in Plan 3:** an on-screen deck, tap/click to reveal the answer, tracks which ones the kid keeps getting wrong so those resurface more. A printable export is explicitly secondary/optional per the spec ("not a requirement every deck must satisfy equally well") -- deferred, see Plan 3 scope decisions below.
9. **Confidence-building and engagement are two distinct mechanics, implemented in Plan 3, never collapsed into one generic "gamification" feature:** low-stakes practice mimicking the real exam's format with a visible progress indicator (confidence), versus points/streaks on the flashcard/review experience (engagement).

Non-goals, from the design doc directly: no mobile app, no multi-family/teacher platform, no paid TTS, no other country's curriculum, no general-purpose spaced-repetition engine unless a simpler mechanic proves insufficient.

## Plan 2 scope decisions (judgment calls the spec explicitly left to the builder)

1. **Topic-tagging taxonomy:** a `subject/topic` string key, matching Plan 1's own grounding vocabulary exactly, with an optional free-text `competency` field on each question for finer-grained tagging when the content-generating agent (Plan 3) wants it. No separate formal competency hierarchy in v1 -- the spec noted MINEDUCYT's own published structure varies by subject (Matemática has more formal structure than Lenguaje for this grade range) and asked the builder to size this to what's actually implemented, not to invent a taxonomy ahead of real content.
2. **Topic-strength thresholds:** `insufficient_data` below 2 questions for a topic, `needs_work` below a 70% correct ratio, `solid` at or above it. Both numbers are a deliberately simple first version per the spec's explicit "start simple" permission -- revisit once real exam data from the user's own kids exists to calibrate against.
3. **Results-export shape (found live, not anticipated):** the browser's self-grading script exports only `{question_id, given_answer, correct}` per question -- it does not duplicate each question's `subject`/`topic` into every downloaded row, since the original exam file (still available locally to whatever re-invokes `study-coach`) already carries that. The eventual fix (below) superseded the first version of this decision: rather than hand-rejoining `subject`/`topic` onto the raw rows, `scripts/audit_exam.py`'s `score` subcommand calls `grading.score_exam(exam, answers)` directly, which already produces fully-tagged result dicts -- this is the reference pattern for Plan 3's real entry points to follow, not a manual re-join step.
4. **The live page's own grading is never authoritative, found live by a fresh review, not anticipated:** a whole-branch review ran the real client-side self-grading script under node and found it marked every true/false answer wrong (a radio's `.value` is always a string; comparing it against a Python-exported bool via `JSON.stringify` never matches). The fix has two parts, both load-bearing: (a) the page itself now maps a true/false answer back to a real boolean and a multiple-choice/single-select answer back to its original typed option value before grading or exporting; (b) independently of (a), `scripts/audit_exam.py`'s `score` subcommand now recomputes every answer via `grading.score_exam` from the raw `given_answer` values and never reads the downloaded file's own `correct` field at all. (b) is the real safety net -- it means a future bug in the page's own (necessarily separate) JS reimplementation can produce a wrong on-page indicator for the kid, but can no longer corrupt the parent-facing gap report, which is the number that actually matters for this project's stated purpose.
5. **An unreviewed open-response answer must never move a topic's score, found live by the same review:** the original implementation counted a still-`None` result toward a topic's `total` without counting it toward `correct` -- which is mathematically identical to marking it wrong, and could deflate an otherwise-solid topic's ratio before any parent/Claude review ever happened. `aggregate_topic_results` now tracks `pending` separately and excludes it from both `total` and the strength ratio entirely.
6. **Kid-facing exam text is parameterized by language, not hard-coded:** the spec requires delivery language to be an independent parameter, defaulting to Spanish for this family's actual use, for "everything kid-facing." `render_exam_html` was initially shipped with hard-coded English strings (True/False, "Download results") -- found by the same review -- and now takes a `language` parameter with an `es`/`en` label table, defaulting to `es`.

## Plan 3 scope decisions (judgment calls the spec explicitly left to the builder)

1. **Printable flashcard export is deferred, out of scope for v1.** The spec's own language ("secondary, optional... not a requirement every deck must satisfy equally well") is explicit permission to size this down; the digital deck is the real deliverable. Revisit if the family's own printer-equipped use case asks for it in practice.
2. **The confidence-building mechanic reuses the real exam's own question bank and format in a `mode="practice"` variant, rather than a separate practice-specific artifact.** Chosen over building a second, parallel rendering path because it's cheaper and automatically stays in sync with whatever question types Plan 2 supports; the spec's own wording ("mimics the real exam's actual format") asks for exactly this. The stronger design choice -- no download mechanism in the page's source at all, rather than a download that's merely not called by convention -- was deliberate: the spec's panic-vs-fluency framing makes a false "did that count?" scare a real risk worth designing against structurally, not just by habit.
3. **The engagement mechanic is points (+1 per "Got it") plus a streak that resets on any miss, with no levels or badges.** Sized small per the spec's explicit "reasonable for the builder to propose and size small for a first version" permission -- the spec named the *purpose* (counter boredom, stay separate from the confidence layer) not specific mechanics.
4. **Quick answer defaults to flashcards only, no exam.** The spec's own words: "most likely... smaller," without fully specifying. A full exam for a single stuck question would recreate exactly the "too long or joyless" anti-goal the spec calls out directly for the opposite case (a bundle that's too long).
5. **Flashcard session history always accumulates (never replaces by `deck_id`), the opposite convention from Plan 2's exam dashboard dedup.** Found explicitly while writing this plan, to avoid over-applying Plan 2's own fix outside the context it was meant for: exam dedup exists specifically for re-scoring the *same* exam attempt after an open-response review merge, a correction to one event. There is no equivalent "correction" workflow for flashcards -- two reviews of the same deck on two different days are two real, separate study sessions, and the wrong-answer-resurfacing mechanic actually needs every one of them counted.
6. **A resurfaced card's two (or more) appearances aggregate by "any miss counts," found live by a fresh review running the real flip-deck script under node.** The first version gave every appearance of a resurfaced card the same DOM identity (`data-card-id` alone), so the page itself was unusable -- flipping one copy flipped both, and a miss on one copy silently vanished if the other copy was later marked correct, discarding exactly the signal resurfacing exists to catch. Fixed by giving each rendered appearance its own `data-card-index`; the export aggregates per `card_id`, and any `"incorrect"` mark on any appearance wins.
7. **The streak/points display is two running counters updated per click, not a value recomputed from the accumulated marks.** The first version recomputed from `Object.values(marks)` on every mark, which follows JS object key order (and sorts integer-like string keys numerically) rather than the order the kid actually clicked in -- the streak did not reliably reset on a miss, the one rule the engagement layer actually promises. Found the same way as #6, by executing the real script rather than reading it.
8. **The deck itself had no CSS, so "flip to reveal" never hid anything -- found the same way, by rendering a real page.** The front and back divs both rendered visibly from the start; `flip()` toggled a class no stylesheet referred to. This is the flashcard equivalent of Plan 2's Critical true/false bug: client-side behavior that was written to look right in the markup but never actually executed or observed before being called done. Fixed with a hide-until-flipped CSS rule; the lesson (execute the JS, don't just read it) is now stated explicitly in this file precisely because it had to be relearned once already.
9. **The flashcard results export is wrapped with `deck_id`, and `audit_bundle.py` gained a `record` subcommand to re-ingest it.** The first version of `SKILL.md`'s full-bundle recipe told the invoking session to consult `flashcard_history.json` before building a deck, but nothing ever wrote a flashcard session back into it -- the exam side had `audit_exam.py score`; flashcards had no equivalent, so the documented "resurface what the kid keeps missing" flow was a no-op as written. `audit_bundle.py`'s prior single-purpose CLI became a `build`/`record` subcommand pair to make room for the fix, mirroring `audit_exam.py`'s own shape.
10. **Weakness is keyed by `(topic, card_id)`, not `card_id` alone, found by the same review.** Card ids are generated per deck (e.g. "c1", "c2", ...) by whichever session built it, with no uniqueness guarantee across different topics' decks -- a miss on one topic's "c1" was resurfacing an unrelated "c1" in a completely different topic's deck. Scoping by topic (information every history entry and every card already carries) closes the collision without requiring globally unique ids.
11. **Practice mode shows a visible banner, found missing by the same review against the plan's own stated interface.** Task 4's own Interfaces block said the page would be "visibly labeled as practice," but the first version added only the "Show my results" button text, with nothing distinguishing the page from a real exam at a glance. Added an es/en banner shown only in practice mode -- the point of the no-download-mechanism guarantee (#2 above) is undermined if the page otherwise looks identical to the real thing.
12. **`write_bundle_files` deletes any of the three fixed files a call doesn't provide, and `render_topic_index_html` scans the topic directory instead of trusting a caller-supplied record of one call's writes.** The first version only ever added files, so regenerating a bundle without (say) `practice_html` left a stale `practice.html` from a previous generation on disk, and the index -- built from just that call's own `written` dict -- could either hide a file that was still genuinely current or link one that had just been deleted. Both fixed together: deletion keeps disk state honest, and building the index from disk rather than from one call's memory means it can't drift from what's actually there.
